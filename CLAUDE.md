# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Lumina Studio** — an internal AI image/video generation app (Next.js 15 App Router, React 19, plain JavaScript, Tailwind, Zustand). Users type prompts with `@tag` references (uploads `@img1` or saved assets `@priya`), pick a model, and get images (Nano Banana Pro / Higgsfield) or videos (Seedance 2.0 via Higgsfield MCP or BytePlus Ark). The API backend is being migrated from Next.js API routes to Django — see the `backend/` section below.

## Commands

```bash
npm run dev            # local dev server
npm run build          # production build
npm run lint           # next lint (no ESLint config committed — was never set up in this repo, pre-dates the JS conversion)
npm run db:push        # push src/lib/schema.js to Postgres (drizzle-kit)
npm run db:seed        # idempotent seed: bucket, admin user, pricing rows
npm run hf:login       # one-time Higgsfield MCP OAuth (writes .higgsfield-mcp-token.json)
npx tsx scripts/<x>.js # ad-hoc/debug scripts (no test framework exists)
```

Environment: copy `.env.local.example` → `.env.local`. `MOCK_GENERATION=1` runs the whole app without real API calls. `scripts/` load `.env.local` explicitly via dotenv.

## Architecture

### Generation flow (the core path)

- **Image**: `POST /api/generate/image` only *enqueues* (persists references + inserts a `queued` row). The client polls `GET /api/queue/status`, and at position 0 posts `/api/queue/execute`, which awaits the provider inside that one request and returns the finished item. That execute route carries `maxDuration = 300`: a high-res NBP render is 30–60s, but best-of-N fans out N of them plus judge calls, and under Fluid compute concurrent jobs share an instance. **60s here was the old Hobby ceiling, not this project's** — it is Pro with a 300s `functionDefaultTimeout`, and the self-imposed 60s cap was killing jobs under load (see the header comment on the route). If the invocation is killed anyway, the row is stranded in `running` until `reapStaleRunningImages` (`store-db.js`) fails it — that reaper's threshold must always stay above this `maxDuration`.
- **Video**: `POST /api/generate/video` creates a provider task and returns a `queued` item; the client polls `GET /api/generate/video/status?id=...`, which advances the task and downloads the result when done.

Both routes: create a `GenerationItem` row up front (`status: running/queued`), compute cost from the `pricing` table, persist uploaded reference images, then update the row on success/failure. Failures return the failed item as JSON (HTTP 200), not an error status.

### Gemini spend-rate throttle (`src/lib/spend-window.js`)

Google caps Gemini API **spend** on a rolling 10-minute window — separate from RPM/TPM — returning `429 RESOURCE_EXHAUSTED` when crossed ($10/10min on Tier 1, $200 on Tier 2/3). Best-of-N makes the app its own worst offender: N parallel renders per job × `MAX_CONCURRENT` jobs.

**Retrying cannot fix this** — the window is 10 minutes and an invocation lives at most 300s, so a saturated window outlives any in-request backoff. `getQueuePosition` therefore performs *admission control*: a job that concurrency would admit is still held (reported as position 1, with `heldForBudget`/`heldReason`/`retryAfterMs`) until the window has room. The client shows it as a normal pending item with a caption and paces its next poll off `retryAfterMs`. Backoff in `gemini.js` still handles momentary spikes; this handles sustained load.

- Gates **images and Omni video only** — Omni runs on the same `GOOGLE_API_KEY`. Higgsfield/BytePlus must never be held behind a Google budget they don't consume.
- Rows that failed with a 429 are excluded from the window (they were rejected, so they cost nothing) — otherwise one storm suppresses the queue for a further 10 minutes on spend that never happened.
- **`GEMINI_SPEND_LIMIT_CENTS` is in *estimator* cents, not dollars.** Costs come from the admin-editable `pricing` table, whose seeds are explicitly placeholders and which under-read real Gemini cost by ~4×: the burst that tripped a real $10 limit on 2026-07-28 scores only ~231 cents here. Default 150 is derived from that incident, not from Tier 1's nominal $10 — don't "correct" it upward. Raise to ~3000 on Tier 2; `0` disables the gate.
- Forward-progress invariant: an empty window always admits, so a job priced above the whole budget can't be held forever.

### Providers (`src/lib/providers/`)

- `gemini.js` — **Nano Banana Pro (`gemini-3-pro-image`) via `generativelanguage.googleapis.com`, deliberately NOT Vertex AI.** The file header documents measured probes: Vertex silently gates 2K/4K to 1K; generativelanguage honors them. Don't "upgrade" to Vertex without re-reading that header. Hard limit: 14 images per prompt — user images are never silently dropped; the code errors loudly and only identity tiles yield.
- `higgsfield-mcp.js` — Higgsfield via its official MCP (Soul photoreal image + Seedance 2.0 multi-reference video). Auth is OAuth: token file locally, `HIGGSFIELD_MCP_REFRESH_TOKEN`/`HIGGSFIELD_MCP_CLIENT_ID` env vars when hosted (token also persisted to S3 for serverless). Flow: media_upload → media_confirm → generate → job_status poll.
- `seedance.js` — BytePlus ModelArk direct. Note: BytePlus blocks photorealistic faces and this cannot be disabled; Higgsfield Soul is the workaround for realistic faces. **Audio**: `generate_audio` is a top-level boolean on the create-task payload and is the only audio control any video path here has — Higgsfield's MCP Seedance tools expose no audio parameter and Omni's Interactions request has no audio field, so `supportsAudio()` in `config.js` must keep matching `higgsfield` *before* `seedance` (the Higgsfield model names contain "seedance" too). Defaults off; audio is billed on top of the video and the `Seedance 2.0` pricing row does not model it. The setting is persisted on `generations.generate_audio` rather than passed through, because `/api/generate/video` only enqueues and `/api/queue/execute` is what submits — the row is the only thing carrying it between the two requests. `scripts/probe-seedance-audio.js` verifies the round trip end to end but **makes a real billed generation**, so it is never run automatically.
- `kling.js` — **Kling image models via the KlingAI Open Platform** (`Kling Image 3.0` = `kling-v3`, `Kling Image 2.1` = `kling-v2-1`). Contract read from the docs and verified live on 2026-07-30; `scripts/probe-kling-image.js` re-verifies it (free by default, `--generate` makes one real billed image). Key points, all of which have bitten or would have:
  - **Auth is a single API Key** as `Authorization: Bearer <KLING_API>`. The AccessKey/SecretKey → per-request HS256 JWT that most write-ups describe is explicitly *legacy* in Kling's own docs. Don't reintroduce the JWT dance.
  - Host `https://api-singapore.klingai.com` (`KLING_API_HOST` overrides) — Kling documents this as the endpoint for servers outside China; `api.klingai.com` is the older address. Both answered our key.
  - **`POST /v1/images/generations` takes ONE reference image** (`image` is a scalar). Multi-reference is a *different* endpoint, `POST /v1/images/omni-image`, with an `image_list[]` and only `kling-v3-omni`/`kling-image-o1` — neither wired up. So >1 resolved `@tag` is a loud error naming Nano Banana Pro as the multi-reference path, never a silent drop of the extras. Kling Image 3.0's "free multi-reference images" blurb refers to that other endpoint; the capability map's "Multi-image to Image" row is `—` for `kling-v3`, and that is what governs.
  - **Prompt cap is 2500 characters, enforced.** Prompts here reach 18 kB, so this fires on long shot-spec prompts — it errors with both numbers rather than truncating away scene detail.
  - **`aspect_ratio` is ignored in image-to-image** (probe-measured; undocumented). With one 800×600 reference, requesting `1:1` and `21:9` both returned 1168×864 — *byte-identical* dimensions following the reference. Text-to-image does honour it. Because `generations.aspectRatio` is what `packColumns` lays the library grid out from, the route **measures the returned image** and stores `nearestKlingAspectRatio(w,h)`; storing the requested ratio would both mislabel the card and give it the wrong shape in the masonry. Nearest-by-*log*-distance, because Kling also rounds text-to-image output to pixel multiples (16:9 → 2720×1536 = 1.771, so an exact match never hits) and ratio error is multiplicative.
  - 1K/2K only — 4K is `kling-v3-omni`. Requesting 4K errors rather than returning 2K under a 4K label.
  - Never sends `negative_prompt` (unsupported whenever `image` is set), nor `image_reference`/`image_fidelity`/`human_fidelity` (endpoint doc scopes them to v1/v1-5; the capability map disagrees for v2-1 — omitting is the safe reading, probe before adding), nor `element_list` (needs Kling's Element Library).
  - References are re-encoded by `prepKlingReference`: Kling accepts **jpg/png only** and this app allows WebP. It also enforces Kling's ≥300px and 1:2.5–2.5:1 limits, erroring rather than upscaling or cropping the user's reference.
  - **`src/lib/kling-input.js` adapts the assembled payload to Kling's one-image, one-string endpoint** — the analogue of `omni-input.js`, and the thing that makes the shared `@tag` system actually work here (added 2026-07-31 after reading 14 real generations). Kling has no multi-part content, so the binding NBP gets from a text header sitting immediately before each group's images has nowhere to live; everything in that module reconstructs it inside the single prompt field. It fixes three faults: references were counted from the raw **uploads** so a saved `@slug` asset resolved into a group and then went nowhere; the prompt reached Kling as `assembled.instruction`, i.e. verbatim, so it arrived carrying literal `@img1` / `@img2` / `@img1-inspired` with one unlabelled image and no legend; and `shotInstruction` was built and ignored. Identity **tiles are never sent** — they are a Gemini bandwidth trick, and spending Kling's single slot on a face crop instead of the user's reference is a straight downgrade.
    - The reference limit is now enforced against what the prompt **resolved to**, not how it was attached, and it counts images rather than groups (untagged uploads collapse into one `SUBJECT` group holding several angles, so counting groups would let 4 through).
    - The role-rule header is emitted **only when `shotInstruction` is absent**. `PROMPT_SHOT_SPEC=1` is on in this deployment, and its `REFERENCES:` legend is role-aware and already binds the image — emitting both duplicated the binding and contradicted it (measured: the legend said "the exact visual style/grade to match" while the header asserted "reproduce exactly what this shows"). Its wording is condensed from `KIND_RULE`/`ROLE_RULE` rather than reused, because those run ~700 chars against a 2500-char cap that real prompts here already exceed.
    - A dangling `@imgN` resolves to the one reference in play (with a single image attached there is nothing else it can mean); with **no** reference attached it is a loud error, because rendering it costs a real generation and saying so costs nothing.
    - `MENTION_REGEX` / `TAG_REGEX` are module-level and `/g`, so this module **clones them** (`new RegExp(...)`) exactly as `mentions.js` does — using them directly leaves `lastIndex` advanced for every other caller in the process. Pinned by a test that calls the builder four times and compares.
    - Reasoned, not bake-off measured: the substitution phrasing ("the reference image") and the condensed rule wording were not A/B'd. What *is* measured is the input side — the tags and dropped references above came from reading production rows.
  - **Kling is the only provider here that reports its own billing.** The finished task carries `final_unit_deduction`, and 1 Unit = $0.0035, so `/api/queue/execute` replaces the enqueue-time estimate with `klingUnitsToCents(...)`. Measured: 2.1 text-to-image billed 4 units, 3.0 and 2.1-with-reference billed 8 — all exactly matching the published list price.
  - Pricing is **flat across 1K/2K** (`IMAGE_RESOLUTION_FLAT` in `pricing.js`), unlike every other image model, and 2.1 charges **double for image-to-image** (the `Kling Image 2.1 · image-to-image` row, which *replaces* the base rate — unlike the audio rows, which are surcharges).
- `omni.js` — Gemini Omni Flash (`gemini-omni-flash-preview`) video via Google's Interactions API; default wire path generativelanguage with GOOGLE_API_KEY, `OMNI_USE_VERTEX=1` switches to Vertex (OAuth/ADC, allowlist-gated); probe-measured contract in the file header (AR 16:9/9:16 only via `response_format.aspect_ratio`, resolution not controllable, duration a real enforced request field — a protobuf-Duration string like `"4s"` under `response_format.duration`, not prompt text; there is no `task` or `delivery` field, unlike what the docs/most video APIs imply — re-probe before trusting memory here, see the file header and `.council/omni-video/decisions.md` D11); unlike the older video paths it consumes the full `assemblePrompt`/shot-spec system via `src/lib/omni-input.js`.
- Models offered in the UI are declared in `src/lib/config.js` (`MODELS`); routes dispatch on model name (`isHiggsfieldModel`, `isKlingModel`, `/nano banana/i`).

**Higgsfield is out of the UI (2026-07-30) but still in the backend.** Only the two `MODELS` picker entries were removed; `providers/higgsfield-mcp.js`, `isHiggsfieldModel`, the pricing rows, the admin token card and the status check all remain, so historical generations still render with their model name and the route dispatch still works. Deleting the backend is a separate step.

Two things broke when those entries were removed, both worth knowing before removing any other model:
- **`DEFAULTS.video.model` still named `"Higgsfield Seedance 2.0"`.** `restoreComposerDraft` validates the persisted model against `MODELS` and falls back to `DEFAULTS`, so a default that isn't in the list leaves the composer on a model the picker cannot display — and still routes to that provider. Now `"Seedance 2.0"`, pinned by `defaultsAreOfferedModels` in `config.test.js`.
- **The Seedance hint said "use Higgsfield for those"** — advice pointing at an option the user could no longer select. Model `hint` text must not name other models unless they're in the picker.

### Video shot directive (`src/lib/video-directive.js`)

Single source of the identity/style scaffolding for **both** Seedance paths (native BytePlus + Higgsfield MCP). They previously carried separate hand-written directives that had already drifted; don't reintroduce a provider-local one.

It owns the **whole** assembly — scaffolding, then the user's prompt verbatim, then a closing precedence rule — because the precedence rule must land *after* the prompt, which the old `DIRECTIVE + prompt` shape made impossible.

Three faults it fixes (reported 2026-07-28):
- **Style was assumed photoreal.** Both old directives locked identity but never told the model to follow the reference's *style*, and the identity wording was photoreal vocabulary ("keep moles, scars, freckles", "do not smooth or idealize") that actively fights an anime/cel-shaded/painterly reference. Style now follows the reference explicitly; the skin-texture clause appears only when the prompt indicates photographic work. **No vision call is used to classify style** — it would spend on the same rate-limited key `spend-window.js` protects, and the model can already see the reference.
- **Our cinematography overrode the user's.** "Keep the subject in sharp foreground focus" is a depth-of-field decision that contradicted any prompt asking for deep focus or a rack focus — while the same directive also said "execute exactly as written", so the model got two conflicting instructions. Defaults are now dropped when `hasCameraDirection` fires, *and* the default block carries its own "apply ONLY where the PROMPT does not specify" conditional so a missed regex degrades to a deferring default rather than a contradiction.
- **Precedence was unstated.** A closing rule now names the exact dimensions (style, medium, framing, focus, camera movement, pacing, staging) on which the prompt outranks us.

Identity lock is *retained* — it's the measured lever — but scoped to identity, not composition. Regex detection is deliberately asymmetric: a false negative keeps today's defaults, a false positive only drops guidance; bare "framing"/"blocking" are excluded as measured false positives.

**Not bake-off measured.** The inherited identity wording was; this restructuring is reasoned. `SEEDANCE_LEGACY_DIRECTIVE=1` restores the previous directives on both paths without a deploy.

### Identity/consistency system (@tags → structured prompt)

This is the most engineered part of the app; the design decisions were measured in bake-offs, not assumed:

1. `src/lib/mentions.js` parses `@imgN` (ad-hoc uploads) and `@slug` (saved assets from the `assets` table) out of the prompt.
2. `src/lib/prompt-assembler.js` builds an `AssembledPrompt`: a text instruction with the SCENE kept literal, plus per-tag **groups** of reference images with role headers (CHARACTER/OUTFIT/LOCATION/...), plus **identity tiles** (face crops sent as extra images — Gemini ingests each image as a flat ~258-token tile, so tiles carry the facial detail).
3. For locked faces, the image route runs **best-of-N** (`FACE_BEST_OF`, default 2, max 4): parallel generations, each scored by `src/lib/middleware/face-judge.js` against the reference face, best one kept, cost billed per candidate. Best-of-N is the proven identity lever; single-pass tricks and face-fix second passes were both disproven (see `gemini.js` header).

### Auth & data

- Custom auth, admin-managed users (no self-signup): HMAC-signed stateless cookie `lumina_session` (`src/lib/auth.js`). `src/middleware.js` is only a cheap edge presence-check for redirects/401s; **real enforcement is `getSession()`/`requireUser()`/`requireAdmin()` inside route handlers.** `GET /api/media/[...path]` did NOT follow this pattern until 2026-07-15 (CRITICAL fix — see Media storage below); if you add a new route, check it calls `getSession()` explicitly, don't assume `middleware.js` covers it.
- Postgres via Drizzle (`src/lib/schema.js`): users, projects, folders, generations, assets, pricing, activity_logs, canvas_boards. Timestamps are **bigint ms** (`Date.now()`), IDs are app-supplied `crypto.randomUUID()`. Data access lives in `src/lib/*-db.js` (store-db = generations, assets-db, projects-db, pricing-db, canvas-db) via `getDb()` in `src/lib/db.js` — never a module-level client, so the backend switch below works everywhere.
- Per-user cost attribution: every generation stores `costCents` (from the admin-editable `pricing` table) and `userId`; `/admin` dashboard reads these plus `activity_logs`.
- **DB backend switch**: `DATABASE_BACKEND` env var — `railway` (default, `postgres` driver via `DATABASE_URL`) or `cloud-sql` (`@google-cloud/cloud-sql-connector` + IAM auth via `pg.Pool`, no static password). `getDb()` in `src/lib/db.js` lazily picks and caches whichever backend is active; GCP infra lives in `infra/gcp/` and `upgrade.md`. Currently staged but **not flipped** in Vercel (`DATABASE_BACKEND=railway` in both production and preview) pending a final maintenance-window cutover — see `progress.md`.

### Media storage

- **Backend switch**: `MEDIA_BACKEND` env var — `s3` (default, `@aws-sdk/client-s3`, bucket from `AWS_S3_BUCKET_NAME`) or `gcs` (`@google-cloud/storage`, WIF/OIDC auth via `src/lib/gcp-auth.js`, no service-account keys). **Production runs `gcs`** — confirmed 2026-07-29 from a live signing error, correcting an earlier claim here that both environments were on `s3`. `src/lib/storage.js` exposes `checkStorageConnectivity()` for a backend-agnostic reachability probe, used by the admin Status tab. `src/lib/save-media.js` is the app-facing wrapper (its function signatures are kept stable across storage backend migrations). Currently staged but **not flipped** (`MEDIA_BACKEND=s3` in both production and preview) — the GCS object audit still has a discrepancy to resolve first (see `progress.md`).
- Objects are addressed through `GET /api/media/[...path]`, but that route **redirects rather than proxies** — it checks the session, resolves which object answers the request, and 307s the browser to a URL it can fetch itself (a CDN URL if `GCP_MEDIA_CDN_URL` is set, otherwise a signed one). Provider result URLs expire, so results are always downloaded and re-stored.
  - **It proxied every byte until 2026-08-05, and that is what made it time out.** With no CDN configured and signing believed impossible, a `<video>` that read its moov atom and abandoned the connection held a whole invocation to the 300s ceiling; a burst of those is the Vercel 504 alert of 2026-08-04. Three things were wrong at once and all three are fixed: no `maxDuration` on the route (it inherited 300), no client-abort propagation (`request.signal` now reaches the GCS read stream and the sharp pipeline, and a disconnect returns 499 so it stays out of the 5xx rate), and no upstream timeout (`MEDIA_OPEN_TIMEOUT_MS`, default 15s, bounds the metadata/GetObject round-trip that runs before any byte is sent).
  - **Signing under WIF does work** — the claim that it "cannot work at all there" was wrong, and the fallback it justified was masking a missing IAM grant. `@google-cloud/storage` wraps the injected `authClient` in a `GoogleAuth`, whose `sign()` resolves a `BaseExternalAccountClient` to its impersonated service account and signs via the IAM `signBlob` API — no private key needed. What was missing is `roles/iam.serviceAccountTokenCreator` for the runtime SA **on itself**: `signBlob` is called with the SA's own impersonated token, so the pool principal's binding doesn't cover it. Command and verification in `infra/gcp/README.md`.
  - `signReadUrl` pins `accessibleAt` instead of letting it default to now, because the V4 signature covers `X-Goog-Date` — without pinning, two requests a second apart mint two different URLs for the same immutable object and the browser cache (keyed by URL) misses every time. `browserMediaUrl` rounds it to a bucket (`MEDIA_SIGNED_URL_BUCKET_HOURS`, default 6) so every request in that window gets the byte-identical URL, and the redirect itself is `Cache-Control: private` — never shared-cacheable, since the redirect is the auth-gated part.
  - The route **falls back to proxying** whenever no browser URL can be produced, so a broken IAM grant degrades to the old behaviour rather than to broken media. That makes the failure invisible from the outside, which is why **Admin → Status → Media Delivery** exists: it reports `cdn` / `signed` / `proxy` and is the only place the difference shows.
- **Thumbnails are rendered on write, not on read** (`src/lib/media-derivatives.js`). `?w=N` used to run a sharp decode + webp encode per grid card per view, on the instance every other request shares. The source object is immutable, so the answer for a given (key, width) never changes — it is write-path work. `uploadBuffer` renders a two-step ladder (512/1280) for raster keys; the route maps a request to the smallest step that covers it, and to the original above the top step so nothing is ever upscaled. Every step is written even for a narrow source, so "derivative absent" has exactly one meaning and the read path can act on it. A miss is rendered once and persisted (`renderThumbnail`), so the ladder is self-healing and `npm run media:thumbs -- --apply` is a warm-up, not a correctness dependency.
  - The `thumbs/<width>/<original key>.webp` namespace embeds an arbitrary key, so the `settings/`/`migrations/` denylist has to see *through* it — `thumbs/512/settings/token.json.webp` starts with `thumbs/`. `isProtectedMediaKey` in `storage.js` is the single shared test and checks the de-thumbed original too; pinned by `media-derivatives.test.js`. No such object can exist today (settings blobs go through `writePrivateBuffer`, which never renders thumbnails, and `.json` isn't rasterisable) — the check is there because that is the assumption the 2026-07-15 finding punished.
- **`?inline=1` forces the same-origin proxy**, and three kinds of caller need it: `fetch(...).blob()` (a cross-origin fetch needs bucket CORS and fails opaquely without it), `extractFrame`'s canvas draw (cross-origin taints the canvas, so `toDataURL` throws), and `<a download>` (browsers ignore the attribute on a cross-origin href and navigate instead of saving). `inlineMediaUrl` in `utils.js` is the one way to build it; the call sites are `addReferenceFromUrl` / `addReferenceFromVideo` / the clone-settings reference restore in `store.js`, and the download anchor in `MediaCard`/`ConversationPanel`/`DetailModal`. All are user-initiated and one-at-a-time, so proxying them costs nothing worth optimising — unlike the feed, which is what the redirect exists for. Configuring bucket CORS would let the first two go direct; nothing depends on that today.
- **Handing an object to an external provider** (BytePlus fetching a `video_url`) needs a URL with no session. `storage.signStoredRef` tries, in order: the public CDN if `GCP_MEDIA_CDN_URL` is set, then a cloud presigned URL, then `/api/media-grant` — an HMAC-signed, short-TTL, single-object grant (`src/lib/media-grant.js`). The grant route is exempted in `src/middleware.js` (its 401 would otherwise fire first) but is not unauthenticated — the object path comes out of the signature, never the querystring, and the `settings/`/`migrations/` denylist is enforced at both mint and verify. The grant fallback is what made video-to-video work when signing was failing in production; that failure is now understood as a missing IAM self-binding rather than an impossibility (see above), so the middle step is expected to succeed once that grant is in place — keep the fallback anyway, it costs nothing and covers a revoked binding.
- **This route requires an authenticated session** (`getSession()`, 401 if absent) and denies any key under the `settings/` or `migrations/` prefixes (secrets / DB dump snapshots that share the bucket with user media) — both added 2026-07-15 after a CRITICAL finding that the route previously had no auth check at all. If you add a GCS/S3 IAM grant for this bucket (e.g. for CDN), it must carry the same prefix exclusion — see the comment in `infra/gcp/bootstrap-media-cdn.sh`.

### Frontend

Single-page app: `src/app/page.jsx` composes the panels; all client state is one Zustand store (`src/lib/store.js`). Right panel has Project | History | Favorites tabs; projects/folders organize generations. Reference images are downscaled client-side before upload to fit Vercel's 4.5MB payload limit — keep that in mind when touching upload paths.

### Library feed: scoped server queries, not a client-filtered window

Every asset view (All assets, a project, a folder, Unsorted, Favourites, each with a kind/search filter) is a **scope**, and each scope is answered by its own indexed query. Before 2026-07-29 there was one global `items` array — `/api/history` had no WHERE clause at all, returned global history 20 rows at a time, and every view filtered that window client-side. Consequences, all reported as separate bugs but all this one cause: an old project rendered empty with every folder counting `0` until the user had scroll-paged through all newer history; search only matched loaded rows; the chat thread for an old project was blank.

- `src/lib/store-db.js` — `queryHistory(filter, cursor, limit)` and `countHistory`/`countScope`. **Pagination is a row-value keyset** (`(created_at, id) < (…)`), never an offset: offsets re-scan everything before them and shift under the concurrent inserts this table constantly gets. The trailing `id` is load-bearing — `createdAt` is a ms bigint and batch generation writes several rows in one millisecond, so a cursor on `createdAt` alone skips or repeats rows at page boundaries.
- Favourites order by `favorited_at`, everything else by `created_at`. `scripts/optimize-history-indexes.js` backfills `favorited_at` for legacy favourites precisely so it can carry a keyset — a NULL there falls outside the row comparison and would strand those rows forever.
- `src/lib/history-query.js` — the one filter⇄querystring parser, shared by the feed route, the counts route and the client. `folderId=none` means "in the project, in no folder" and must stay distinguishable from an absent `folderId` ("any folder").
- `src/lib/feed-scope.js` — pure scope logic (`scopeKey`, `scopeToQuery`, `matchesScope`, `compareInScope`). `matchesScope` must stay equivalent to `filterConditions` in `store-db.js`: stricter and a finished generation vanishes until reload, looser and a row appears that a refetch removes. Unit tests in `feed-scope.test.js`.
- Store: `items` is the **active scope's** page, not a global pool. Scope changes are driven by one subscription at the bottom of `store.js` (search debounced 300ms), each read is sequence-guarded so a slow reply can't paint over a newer one, and scopes are LRU-cached (`src/lib/feed-cache.js`) so re-entry is instant with background revalidation. Rows live in several pools at once, so mutations go through `patchEverywhere`/`dropEverywhere` — updating only `items` gets silently reverted by a stale cache entry on the next tab switch.
- **Never call `putFeedCache` while iterating the cache.** It deletes and re-inserts the key to maintain LRU order, and a JS `Map` iterator visits entries added during iteration — so the key is revisited forever. That shipped once and hung the tab a few seconds after every Generate, because `patchEverywhere` runs on each poll tick of an in-flight job. `patchCached`/`dropCached` iterate a snapshot of the keys and write with a plain `Map.set` (which preserves order); patching is not a "use" for LRU purposes anyway. Regression tests in `feed-cache.test.js` all carry timeouts, so a reintroduced loop fails the run instead of hanging it.

**The grid's scroll container has two different parents**, and it must size correctly under both: `HistoryPanel` renders it as a child of a flex *column* (where `flex-1` sizes it), `ProjectPanel` as a stretched item of a flex *row* (where `flex-1` means nothing and `h-full` is what works). `AssetGrid`'s root therefore carries both. Carrying only `flex-1` left it at `height: auto` under `ProjectPanel`, so the scroller — `h-full` of an auto height, i.e. auto — grew with its content instead of scrolling, and the asset list could not be scrolled at all. It only showed once content exceeded the panel height, so it read as "broken on some machines" (reported 2026-07-29 from a second monitor).
- `ConversationPanel` reads its own `threadItems` pool (project-scoped); `CanvasAssetPanel` uses the standalone `useHistoryQuery` hook. Neither may go back to filtering the shared feed — that is what coupled them to the right panel's scroll position.

**Indexes are not created by `db:push`** (a plain `CREATE INDEX` locks the table against writes). Run `npm run db:optimize` — `CREATE INDEX CONCURRENTLY` plus the `favorited_at` backfill, safe to re-run; applied to production 2026-07-29. `scripts/probe-history-query.js` and `scripts/probe-history-counts.js` are read-only verification probes (keyset walks with no duplicates/skips, LIKE-escaping, per-folder counts, `EXPLAIN`).

Do **not** expect every feed query to use a keyset index — measured on production at 895 rows, the planner picks them selectively and that is correct:

| query | plan |
|---|---|
| selective project (44/895 ≈ 5%) | `generations_project_keyset_idx`, index scan, no sort |
| favourites | `generations_favorite_keyset_idx`, index scan, no sort |
| non-selective project (369/895 ≈ 41%) | old `generations_created_at_idx` + Incremental Sort |
| global feed | old `generations_created_at_idx` + Incremental Sort |

The incremental sort is nearly free because `created_at` is close to unique, so its presorted groups hold ~1 row; a narrower index beats a wider composite one at that point. The composite indexes earn their keep as the table grows and any one project becomes a smaller fraction of it. **Correctness does not depend on which index is chosen** — no-skip/no-duplicate pagination and bounded work per page come from the row-value predicate plus `LIMIT`, not from the index (a mid-table cursor reads ~25 buffers regardless of depth). Total added index size: ~208 kB.

### Why the asset grid must not re-layout on scroll

Reported as "it keeps rearranging while I scroll" and fixed 2026-07-29. Four separate causes compounded, so re-introducing any one of them brings the symptom back:

1. `MediaCard` had framer-motion's `layout` prop — every card FLIP-animated to any new position, so each appended page set the whole grid in motion. Hover lift is now a CSS transform for the same reason (`whileHover` animated `y`, an inline style a layout pass has to honour).
2. `ProjectPanel` used a balanced CSS multi-column masonry (`columns-… [column-fill:_balance]`). Column balancing is global: appending a page redistributes *every* card. `src/components/AssetGrid.jsx` is now the single grid for both panels.

   **Layout has to satisfy two properties at once, and each obvious answer only gives one.** Balanced CSS masonry fills the gaps but reshuffles on append. A uniform CSS grid is append-stable but leaves dead space, because a grid row is as tall as its tallest card — with 21:9 and 9:16 side by side that band is very visible (reported 2026-07-29, after the grid shipped). The answer is `packColumns` in `AssetGrid.jsx`: greedy shortest-column masonry computed in JS from each card's aspect ratio. It fills gaps *and* each placement depends only on the items before it, so appending cannot move what is already placed. Heights come from the aspect ratio, never from measuring the DOM, which keeps it deterministic and free of a measure→paint→measure loop. Re-packing does occur on column-count changes (panel resize, zoom) and on a prepend — both direct consequences of a user action, not movement under a passive scroll. Append-stability is pinned by `src/lib/pack-columns.test.js`; it is the property a screenshot cannot verify.
3. `AnimatePresence mode="popLayout"` absolutely-positions exiting children and animates siblings into the gap — right for a short list, wrong for a grid being appended to.
4. `contentVisibility: auto` with a flat `containIntrinsicSize: "200px"`. It is now `auto 240px`; the `auto` keyword makes the browser remember each card's real height, without which the scroller's height changed as cards left the rendering window.

Also: the infinite-scroll sentinel lives *outside* the grid (as a grid child it claims a cell and reflows the last row), and live arrivals are **buffered** into `pendingItems` while the user is scrolled away from the top, surfaced as a "N new items" pill instead of being inserted above the viewport. `setFeedPinned` is called per scroll event and must keep its no-op-when-unchanged guard.

### Admin dashboard: totals come from SQL, never from an array's length

Same lesson as the library feed, learned separately and later (2026-07-30). `/api/admin/data` used to ship the newest **500** generation rows with full prompt text, and the Overview computed every figure from that array in the browser. So each figure silently meant "over the newest 500" rather than over the table:

| symptom | measured on production, 916 rows |
|---|---|
| `Generations` tile | frozen at **500** since the table crossed 500 |
| `Total spend` tile | **$152.74** against **$257.18** actual — 41% missing |
| by-model / by-kind / per-day charts | last 500 only |
| Logs search + model dropdown | matched only loaded rows |
| payload on dashboard open | **2,273 kB**, of which 2,044 kB (95%) was prompt text |

Prompts here average 3.8 kB and reach 21 kB (shot-by-shot video prompts), which is why the log dominated the payload. The internal tell was that the **Users** tab was already SQL-aggregated and therefore disagreed with the Overview.

- `src/lib/admin-stats.js` — `readAdminStats()`: `count(*)`/`sum()`/`GROUP BY` for totals, by-kind, by-model, per-day, and the DISTINCT model list. Day buckets are `to_char(... at time zone 'utc')` **deliberately UTC**, matching the `toISOString().slice(0,10)` the client used, so the chart's buckets didn't shift when this moved server-side. `byKind` returns explicit zeros in fixed order so pie slices don't reorder (and recolour) as the mix changes.
- `src/lib/admin-logs.js` + `GET /api/admin/logs` — the browsable log: server-side filtering, the same row-value keyset as the feed (`(created_at, id) <`, reusing `generations_created_keyset_idx`), and `left(prompt, PROMPT_PREVIEW_CHARS)` **in SQL** so the bulk never leaves Postgres. Truncating is exactly *why* search had to move server-side: matching a truncated prompt in the browser would quietly only search its first 300 characters. `promptTruncated` is a `length() >` flag so the cell can show "…" rather than imply the prompt ended.
- CSV export is a server download (`?format=csv`) covering every row matching the filter with **full** prompts, capped at `MAX_CSV_ROWS`; it used to export only the loaded window.
- `src/lib/admin-activity.js` + `GET /api/admin/activity` — the audit trail, paged the same way (2026-07-31). It was the last flat newest-500 window: `activity_logs` holds **1,174 rows**, so 674 events were simply unreachable, and the action dropdown only offered actions occurring inside that window. The action list now comes from a SQL `DISTINCT` and is sent on the **first page only** — it doesn't change as you page, and it's the one part of the response that scans beyond the page. `detail` is returned whole rather than truncated like prompts: every writer stores a small object and the one that could be large already slices the prompt to 120 chars at the call site.
- `/api/admin/data` now returns **no list rows at all** — just users, `stats`, pricing. **2,273 kB → 8.8 kB on open (259×)**; the log is +49 kB and activity +15 kB, both only on the Logs tab. What's left is bounded by user and pricing-row count, so the route no longer grows with usage. Keep it that way.
- `readHistory()` in `store-db.js` and `readActivity()` in `activity.js` were both deleted when the admin route stopped calling them — the alternative is an unused second way to read the same table that will drift.
- **A cursor belongs to the result set it came from.** Both tabs clear `nextCursor` *before* a filter refetch, not after it resolves. Without that, clicking "Load more" while a filter change is in flight pages the **previous** filter and concatenates two different queries' rows — the sequence guard cannot catch it, because the filter changed before `loadMore` started rather than during it. It surfaced as `Showing 100 of 84 events` with a button reading `Load -16 more`, and it shipped in the 2026-07-30 log work; caught by driving the rendered page, not by any test.

`scripts/probe-admin-payload.js` is the read-only verification for **both** lists (totals vs independent `count(*)`/`sum()`, a full keyset walk of each asserting no skips or duplicates, filter narrowing, ILIKE-escaping, the action list matching `count(distinct action)` and being sent once rather than per page, payload accounting, and it prints the before/after numbers). Filter-parser unit tests in `admin-logs.test.js` and `admin-activity.test.js`.

### Depth-map worker (2026-08-14)

A fourth generation kind — `kind='depth'` — that runs on a machine this app doesn't control or pay cloud rates for, instead of a cloud provider. Model is [Video-Depth-Anything](https://github.com/DepthAnything/Video-Depth-Anything) (ByteDance/CVPR2025, vendored as a plain git checkout at `neural-networks-workflow/video-depth-maps/Video-Depth-Anything`, a sibling repo, not inside this one), optionally composited with YOLOv8-seg person tracking — the exact approach already proven in that sibling repo's `scripts/color_code_depth.py`. Reachable from the nav bar's Depth destination (`TopBar.jsx`), which shows a small dot next to it derived from worker heartbeat recency.

**Why a worker that dials out, not a server this app calls into.** The obvious shape — an HTTP endpoint on the operator's Mac that this app POSTs a job to — doesn't work: that Mac sits behind an ordinary home router with no public IP, and `pyserver/`'s existing local-InstantID service is exactly that shape and only works because in that case the Next.js app and the Python service run on the *same* machine (`LOCAL_AI_URL` defaults to `127.0.0.1:8765`) — it has no path from a Vercel-hosted deployment to a home machine. The depth worker instead polls **out**: `depth-worker/worker.py` makes outbound HTTPS calls to `/api/worker/depth/claim` every few seconds, the same direction a browser tab's own requests go, so nothing needs a port forwarded, a static IP, or a tunnel service. The tradeoff is latency (a job waits up to the poll interval before being picked up, typically a few seconds) for zero exposed surface and zero network configuration — judged the right trade for a single-operator local-compute setup, revisit if this becomes multi-tenant.

**Reuses the `generations` table rather than a new one** (`kind='depth'` alongside `'image'`/`'video'`) — this is what "generations stay on veevee" (the actual product requirement) gets for free: history/feed, favourites, project/folder membership, admin dashboard totals, download-zip, all work on a depth row with zero kind-specific code beyond what's noted below, because they already operate on `kind` generically. Two fields are **reused for a different meaning** rather than adding single-purpose columns:
- `resolution` carries the encoder choice (`vits`/`vitb`/`vitl`) — it plays the same "which quality tier" role for a depth job that it plays for image/video, so this is a reuse, not a repurposing. See the comment on `/api/worker/depth/claim` (and its Django twin in `depth_views.py`) where it's read back out.
- `aspectRatio` is a placeholder (`"16:9"`) at enqueue time, corrected to the *measured* output dimensions on completion — the same pattern `providers/kling.js`'s `nearestKlingAspectRatio` already uses for Kling image-to-image, for the same reason (storing the requested value would mislabel the library card).

Two fields are genuinely new, because nothing existing fits: `progressPercent`/`progressMessage` (nullable, cleared back to null on completion so "absent" always means "not currently reporting progress") and `trackCharacters` (a dedicated boolean rather than reusing `generateAudio` — also a per-job worker-consumed boolean, but for a wholly different kind, which would read as a depth row somehow having an audio setting). A separate `depth_workers` table (one row per worker process, upserted by `workerId` on every heartbeat) backs the status pill — "online" is derived from heartbeat recency at read time (`WORKER_STALE_MS`, 45s) and is never itself a stored flag, so a worker that's killed or loses network self-heals to offline without a clean-shutdown path.

**No admission control, unlike image/video.** `/api/queue/execute`'s whole job is enforcing the shared per-kind concurrency cap and Gemini's spend window — neither applies to a job that runs on hardware this app doesn't share capacity or a Google billing account with. A depth row sits at `status='queued'` until the worker's own claim call picks it up; `claim_next_depth_job`/`claimNextDepthJob` uses `FOR UPDATE SKIP LOCKED` on the oldest queued row (not a plain conditional UPDATE like `lockJob`, which locks a *known* id) so that a second worker — not built today, but the operator's own framing was "queue and load balancer" — could join later with zero query changes: two concurrent claims can't win the same row, and neither blocks behind the other.

**Two auth shapes on the worker-facing routes**, both in `depth-worker-auth.js`/`depth_worker_auth.py`: `generate/depth` and `generate/depth/status` use the normal session cookie (a signed-in user submitting a job), while every `/api/worker/depth/*` route uses one shared bearer token (`DEPTH_WORKER_TOKEN`) — the caller is a Python process with no browser and no login flow. One token for every worker is deliberate, not a limitation: a worker still identifies itself via its own `workerId` in every request body, so a second machine can join under the same token with no auth change. Unset `DEPTH_WORKER_TOKEN` refuses every worker request rather than allowing them through.

**Video bytes never pass through a serverless function.** Both the browser's input-video upload and the worker's result-video upload are, at video sizes, well over Vercel's 4.5MB body limit that every other upload path here stays under by inlining base64 (image references are downscaled client-side to fit; a raw video has no equivalent downscale step). `getSignedUploadUrl`/`get_signed_upload_url` (new, in `storage.js`/`storage.py`, mirroring the existing `getSignedReadUrl`'s S3/GCS dispatch) mints a URL either side can PUT bytes to directly — `/api/uploads/presign` (session-authed, browser-facing, namespaced by `purpose` so upload kinds can't collide) for the input, `/api/worker/depth/upload-url` (worker-authed) for the output.

**RAM cap is soft and best-effort, not OS-enforced** — true hard RSS enforcement needs cgroups, which macOS doesn't have. `worker.py` layers two mechanisms: a best-effort `resource.setrlimit(RLIMIT_AS, ...)` attempt at startup (unreliable on macOS, cheap to try anyway), and a background thread that samples actual RSS every 5s — crossing the configured cap (`DEPTH_RAM_LIMIT_MB`, default 32000 for a 64GB operator machine, confirmed range up to ~48000) stops the worker from **claiming new jobs** until usage drops, and crossing 1.3× the cap hard-exits the process outright rather than let a runaway allocation take the whole machine down. `depth-worker/start.sh` wraps the worker in a restart loop specifically so that hard-exit (and any ordinary crash) recovers on its own instead of silently leaving the status pill red until someone notices — this is also the literal shape of "leave a terminal process open."

**Progress is coarse, not per-frame.** `infer_video_depth` has no progress callback in Video-Depth-Anything's own API (confirmed reading `run.py`), so `worker.py` reports a handful of named milestones (downloading, loading the model, running depth estimation, compositing tracking if enabled, encoding, uploading) rather than a true frame-by-frame percentage. Wiring real per-frame granularity means patching the vendored inference loop — not attempted here.

**Character tracking** (composer checkbox, `trackCharacters`) is a direct port of `video-depth-maps/scripts/color_code_depth.py`'s compositing loop — YOLOv8-seg tracks people only (`classes=[0]`), each tracked person tinted a distinct color on the depth map, output side-by-side with the source frame. Off, the output is a plain grayscale depth video (`run.py`'s own default shape). Roughly doubles per-job processing time (two models per frame instead of one).

**Not live-verified.** Written and read carefully against Video-Depth-Anything's `run.py` and `color_code_depth.py` for exact call shapes, but never run end to end against a real deployment or a real GPU (no network egress to a real API and no CUDA/MPS device in the environment this was built in) — the same caveat this migration's own `higgsfield_mcp.py` port and generation-core phase carry, for the same reason. Verify the first real job carefully. See `depth-worker/README.md` for setup/operation and its own "Not yet done" list.

### backend/ — Django/DRF, replacing the Next.js API (in progress, strangler-fig)

**2026-08-10: migration started.** The entire `src/app/api/*` surface is being ported to Django + Django REST Framework in `backend/`, deployed separately (Railway) from the frontend (Vercel), so the two apps live at different origins. This is **incremental** — Next.js API routes keep serving traffic domain-by-domain until each one has a working Django equivalent the frontend has been switched to; `src/app/api` is only deleted at the very end. The frontend is also being converted from TypeScript to plain JavaScript (`.tsx/.ts` → `.jsx/.js`), independent of the backend migration.

- **Shared Postgres, shared session cookie, two frameworks.** Both apps point at the *same* Railway Postgres during the migration. DB ownership: Django took over migrations from Drizzle immediately (`manage.py migrate` applies Django's own tables — `auth_*`, `django_session`, etc. — additively; existing Drizzle-created tables are untouched). The **full schema was mirrored up front** (2026-08-10, `apps/core/models.py`) rather than per-task, so later phases only add serializers/views against models that already match the live tables — but every one of those models is `managed = TEST_MANAGED` (normally `False`; see `apps/common/db_flags.py`), so Django issues **no DDL** against any Drizzle-owned table in production. `TEST_MANAGED` flips to `True` only under `DJANGO_TEST_MANAGED=1`, which both `apps/common/migrations/0001_initial.py` and `apps/core/migrations/0001_initial.py` read live (not a hardcoded literal) so `manage.py test`'s throwaway database actually has these tables to create test rows in. Routes/services still get added domain-by-domain per the task list — only the model layer was front-loaded.
- **Auth stays split until the last phase.** `apps/common/session_auth.py` is a **verify-only** port of `src/lib/auth.js`'s stateless HMAC `veevee_session` cookie — same payload shape (`b64url(JSON{uid,ver,exp})` + HMAC-SHA256 sig), same `AUTH_SECRET`, same legacy `ver ?? 0` fallback. Django can authenticate requests signed by Next.js from day one (verified live against production-minted cookies); Next.js remains the only *issuer* (login/logout/password) until the auth-cutover phase. **If you change the token shape, algorithm, or secret handling on one side, change it on the other in the same change** — a drift here silently breaks cross-app sessions for every user, not just new logins.
- **Pilot domain done (task #3): Users/Projects/Assets.** `apps/core/{projects_service,assets_service,activity,views}.py` — plain CRUD, verified against live production data (real users, real projects, a real S3-uploaded asset with its full thumbnail ladder, then cleaned up). `ensure_default_project()`'s Postgres advisory-lock key (`815042`) must stay numerically identical to `projects-db.js`'s — a mismatch would let a concurrent Next.js + Django request both pass the check and create two default projects.
- **Media serving (task #4) done: write path (pulled forward into #3) + full read/serving path.** `apps/core/storage.py`, `media_derivatives.py` (pure, direct port of the thumbnail-ladder logic — `THUMB_LADDER` must stay numerically identical to the TS side), `media_grant.py`, `media_views.py` (`GET /api/media/<path>`, `GET /api/media-grant`), `save_media.py` (asset-image functions only so far; `saveBase64`/`saveCanvasAsset`/`saveAvatarImage`/`saveReferenceImages` land with the domains that call them). **GCS auth deviates from the TS assumptions**: `gcp-auth.js` signs via Workload Identity Federation using Vercel's built-in OIDC minting, which has no Railway equivalent — see `storage.py`'s module docstring. ### Frontend: converted from TypeScript to plain JavaScript (2026-08-10)

Independent of the backend migration (the user's own framing: "we ditching typescript entirely"). Every `.ts`/`.tsx` file in the repo — `src/` (190 files) and `scripts/` (28 files), plus `drizzle.config.ts` and the stray root-level `scratch.ts` — is now `.js`/`.jsx`. `backend/` is unaffected (Python). `.council/*.ts` probe scripts were deliberately left as-is: they're archival evidence for past decisions, not active code, and aren't imported by anything.

- **Mechanical conversion via `sucrase`** (type-strip only, no dependency previously in use elsewhere in the app): `transforms: ["typescript"]` (plus `"jsx"` for `.tsx`, using `jsxRuntime: "preserve"` so JSX is re-emitted as raw JSX rather than rewritten to `createElement` calls — verified byte-identical against the sucrase CLI's own output), `disableESTransforms: true` (sucrase's default ES-downlevel behavior injects an `_optionalChain` helper for `?.` even when nothing else about the file needs transforming — unwanted, since the target is Next.js's own build pipeline, not an older runtime), `production: true` (skips the dev-only `_jsxFileName` injection). A trailing pass collapses runs of 3+ blank lines left behind by stripped multi-line type annotations.
- **Next.js auto-detects TypeScript from `tsconfig.json`'s mere presence, not from any file actually being `.ts`.** The first pass converted only `src/`, leaving a `tsconfig.json` scoped to `scripts/**/*.ts` (`scripts/` was still real TypeScript at that point) — `next build` still detected the config, auto-reinstalled `typescript`/`@types/react`, auto-re-added `allowJs`/`jsx: "preserve"`/the `next` plugin/`.next/types` to the config, and then **type-checked the whole `include` set**, which pulled in `scripts/ab-face-eval.ts` and failed on a pre-existing type error there — a standalone probe script outside the app's import graph, not a regression from the conversion. Converting `scripts/` too and deleting `tsconfig.json` entirely (rather than trying to keep a TS-free-but-present config) was the actual fix; a `tsconfig.json` and "no TypeScript in the build" are mutually exclusive as far as Next's build is concerned.
- **`jsconfig.json`** (new) carries the `@/*` → `./src/*` path alias for both Next's own webpack resolution (confirmed via a clean `npm run build`) and editor tooling. It intentionally does **not** replace `tsconfig.json` for `tsx`'s path-alias resolution — `tsx` (via `get-tsconfig`) only auto-discovers a file literally named `tsconfig.json`, so the `@/*` alias breaks under `npx tsx --test ...` without one. Fixed by pointing `tsx` at the alias config explicitly rather than reintroducing `tsconfig.json`: **`npx tsx --tsconfig jsconfig.json --test ...`** — `get-tsconfig` parses any path given to `--tsconfig` regardless of filename, since it's format-compatible with `tsconfig.json`. This is now the required invocation for the unit test suite (see below); the old `npx tsx --test ...` form silently drops the `@/*` alias and fails any test importing a component or lib module through it (caught this way: `pack-columns.test.js` — importing `AssetGrid.jsx`, which imports `@/lib/store` — was the only failure in an otherwise-passing 329-test run).
- **`scripts/*.js` still run via `tsx`, not plain `node`**, even though they're no longer TypeScript — they use extensionless relative imports (`../src/lib/db`), which `tsx`/esbuild resolve but plain Node ESM does not without explicit extensions. `tsx` stays a devDependency for this reason; `typescript` and the `@types/*` packages do not.
- `drizzle.config.ts` → `drizzle.config.js`: `schema` now points at `./src/lib/schema.js`; the `satisfies Config` type assertion was dropped (had no runtime effect).
- **Verified**: clean `npm run build` (zero TypeScript involvement — confirmed `typescript` does not get reinstalled into `package.json` on a rebuild once both `tsconfig.json` is absent and no `.ts`/`.tsx` file exists anywhere outside `backend/`), the full unit suite (329/329 passing under the `--tsconfig jsconfig.json` invocation), and a manual browser pass against `npm run dev` (`/login` renders with full styling, no console errors, controlled input state updates correctly) — full generation/auth flows weren't exercised live here since that would require real credentials, but this task's scope was the mechanical TS→JS conversion, not a re-verification of behavior already covered by the unit suite and the task #1–#9/#12 backend work.

- **Migrations**: every model stays `managed = TEST_MANAGED` (see `apps/common/db_flags.py`) — Django issues no DDL against these tables in production regardless of which app owns the model class, so this refactor carried zero production schema risk. Each new app got its own `migrations/0001_initial.py` (generated the same way the originals were, `DJANGO_TEST_MANAGED=1 manage.py makemigrations <app>`); `apps.media` and `apps.admin_dashboard` have no models and so no migrations directory. `apps.common` got one additive migration for the newly-added `ActivityLog` model rather than a squash, so its existing 2 migrations stay as historical record.
- **Shared test fixtures**: `SECRET`/`_cookie_for`/`_make_user` (mint a valid session cookie and a throwaway `User` row without going through the real login flow) were previously defined once in `apps/core/tests/test_pilot_history_media.py` and imported by four other test files — now `apps/common/test_utils.py`, since `apps.common` is the one app every other app's tests can already depend on. `test_pilot_history_media.py` itself (407 lines, 13 test classes spanning 4 domains) was split by class along the same app boundaries: `ProjectsServiceTests`→`apps/projects/tests.py`, `AssetsServiceTests`→`apps/assets/tests.py`, `PilotDomainAuthTests`+the former `test_auth.py`→`apps/common/tests/test_auth_views.py`, the media classes→`apps/media/tests.py`, the history classes→`apps/generation/tests/test_history.py`.
- File names were kept as-is during the move (e.g. `apps/canvas/canvas_db.py`, not renamed to `db.py`) — a deliberate choice to keep the change a mechanical "move + fix imports" rather than "move + rename + fix imports", minimizing the chance of a typo'd cross-reference in a ~60-file reorganization.
- **Verified**: `py_compile` across the whole tree, `python manage.py check` (Django's own system-check, catches bad `AppConfig`/`INSTALLED_APPS`/URL wiring) clean after every single app extraction (not just at the end), `DJANGO_TEST_MANAGED=1 manage.py makemigrations --check` reports no missing migrations, and the full test suite at 346/346 passing — the same count as before the split, since this reorganizes tests rather than adding or removing coverage.

### Running the Django suite: Postgres is required for a trustworthy result

`DJANGO_TEST_MANAGED=1 AUTH_SECRET=<any value> DATABASE_URL=<postgres URL> python manage.py test` against a **real Postgres** database — Railway, Cloud SQL, or a local `docker run -p 5432:5432 -e POSTGRES_PASSWORD=x postgres:16` — is the only way to get a number worth trusting. `manage.py test` creates and destroys its own `test_<dbname>` database automatically, so pointing this at the same Railway instance production uses is safe (it never touches the real `railway`/`postgres` database) as long as the connecting role can create databases.

Pointing `DATABASE_URL` at SQLite instead (easy to do by accident — `django-environ`'s `env.db()` parses a `sqlite://` URL without complaint) does **not** fail at startup. It fails ~60 tests deep into the run with opaque errors (`OperationalError: unrecognized token: ":"` for a `::int` cast, `no such function: pg_advisory_xact_lock`) that read like real bugs but are purely an engine mismatch — this backend uses Postgres-only raw SQL throughout (advisory locks in `projects_service.py`/`queue_service.py`, `jsonb` in canvas board state, `ILIKE`/`to_char(...at time zone 'utc')` in the history and admin-dashboard queries) with no ORM-portable equivalent, and none of it is optional. `apps/common/checks.py` (`common.W001`, registered via `CommonConfig.ready()`) now catches this at `manage.py check`/`test` startup and prints one clear warning naming the actual cause, instead of leaving a wall of unrelated-looking failures to puzzle through. It's a *warning*, not a hard failure — a real subset of the suite (`apps.media`, most of `apps.admin_dashboard`'s parser tests, `apps.canvas`'s serialization tests, and every pure-logic provider test ported from the TS suites) genuinely passes against SQLite, which is useful in a sandboxed/CI environment with no Postgres reachable at all (no root, no Docker, no egress to an external DB — the exact situation this note was written from). Set `DJANGO_ALLOW_NON_POSTGRES_TESTS=1` to silence the warning when that quick-subset run is deliberate.

### Higgsfield–NBP parity (flag-gated enhancements)

Research (July 2026) found Higgsfield's edge over baseline NBP was not hidden API magic, but deterministic scaffolding (role-aware reference headers, subject-framing language, reference fidelity via higher client upscale cap) plus a widened best-of-N judge (identity + prominence + sharpness composite). All behaviors ship **off by default** and are env-flag gated; deploy Stage 2 can A/B old vs new cheaply.

- **`PROMPT_SHOT_SPEC=1`**: `assemblePrompt` emits a structured instruction with a reference legend, role-labeled image headers, wide-AR framing coda, and an in-prompt NEGATIVE block, keeping the raw user prompt verbatim. Implemented in `src/lib/shot-spec.js` (pure, unit-testable).
- **`PROMPT_ROLE_DETECT=1`**: Fallback role classifier for `@imgN` uploads using extended Gemini detection. Only consulted when `PROMPT_SHOT_SPEC=1`. Non-blocking cross-check WARN surfaces upload-order mismatches.
- **`JUDGE_COMPOSITE=1`**: Best-of-N judge scores identity + prominence + sharpness in one Gemini call and selects by composite subject to an identity floor (guarantees identity never regresses). `selectBestCandidate` in `src/lib/middleware/face-judge.js`.
- **`POST_CRISPEN=1`**: Classical sharpen-only delivery pass (no artifacts, ~110ms per image).
- **`SUPERSAMPLE=1`**: Render one resolution step up, downsample to requested size. Measured highest prominence but 1-of-4 scene-accuracy risk (outfit dropped); flag off by default, use for hero shots only. Operationally: combining it with `FACE_BEST_OF>1` is expensive and slow — it was previously unsafe against the 60s cap, which is now 300s, but it still multiplies the parallel-render count that trips Gemini's spend-based 429.
- **`NEXT_PUBLIC_REF_MAX_DIM` (default `2048`)**: Client reference longest-side cap (was hardcoded 1024). `PromptComposer.jsx` includes a budget ladder (2048/q0.85 → q0.7 → 1536/q0.8 → 1024/q0.8) to stay under Vercel's 4.5MB body limit with high-fidelity refs.

Unit tests: **`npm test`** (Node built-in `node:test` + `node:assert`; no new dependency). This runs `tsx --tsconfig jsconfig.json --test $(find src -name '*.test.js' | sort)` — every `*.test.js` under `src/`, discovered at run time rather than hand-listed. An explicit per-file list used to live here and in `package.json`; it silently fell 14 files behind as new test files were added (last measured: the documented command only ran 329 of the real 540 tests, missing all of `auth.test.js`, `password.test.js`, `login-throttle.test.js`, `prompt-assembler.test.js`, `zip.test.js`, `gemini-parts.test.js`, `limits.test.js`, `status-checks.test.js`, and everything under `canvas/` and `agents/`) — a file can be added and never actually get run by anyone following this doc. Don't go back to a hand-listed file argument for this reason. **`--tsconfig jsconfig.json` is required** since the TS→JS conversion removed `tsconfig.json` — without it, `tsx` can't resolve the `@/*` path alias and any test importing through it fails. **Bare `node --test`/`tsx --test src` (directory-scan mode) does not work here** — tsx's loader intercepts a bare directory argument as a module specifier rather than letting node's test runner walk it, so the file list has to be expanded by the shell (`find ... | sort`) and passed as explicit arguments; this is also why `scripts/*.test.js`-shaped files must never exist (there are none today, but node's default test-file glob would otherwise sweep in `scripts/`'s live-API probe scripts, e.g. `scripts/higgsfield-test.js`, which fail without real provider credentials rather than being unit tests at all). For full evidence and per-image metrics, see `.council/higgsfield-nbp-parity/`; for the Omni video integration, see `.council/omni-video/`.

## Working conventions

- No over-engineering and no quick hacks: when a provider limit bites (image caps, aspect-ratio rules), solve the root problem architecturally rather than silently filtering/dropping user inputs.
- Back provider/payload changes with official docs or an empirical probe script (`scripts/` has many examples); several provider schemas here were deduced by testing because docs were wrong or missing.
- `progress.md` holds session handoff notes; comments at the top of `gemini.js` and `prompt-assembler.js` record measured decisions — read them before changing generation behavior.
