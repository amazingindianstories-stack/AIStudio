/goal

Migrate Veevee V1 from its current Next.js/Drizzle backend architecture to a Django + Django REST Framework backend, using the CURRENT production repository as the sole authoritative definition of product behavior and data semantics.

This migration is a committed architecture decision.

Django is not an experiment, optional parallel implementation, preview-only mirror, or temporary alternative.

The final architecture must be:

- Next.js = frontend/application shell only
- Django + DRF = sole authoritative HTTP API/backend runtime
- Django ORM + Django migrations = sole authoritative database model/schema system
- PostgreSQL = production relational database
- GCS / existing storage infrastructure = production media/object storage
- Python/Django workers = eventual authoritative asynchronous worker runtime
- Vercel = frontend hosting
- Railway = Django API and worker hosting
- local GPU/depth workers remain external workers communicating with Django
- no duplicate Node and Django business backends remain at completion

The migration must be performed incrementally and safely against the latest production architecture.

Do not start by recreating historical Django models verbatim.

Do not assume any historical Django implementation is current.

The current production repository, current PostgreSQL schema, current business invariants, current tests, current APIs, current worker protocols, current media/export behavior, and current deployed architecture define what Django must implement.

Historical Django code and Git history are useful only as reference and reusable implementation material.

==================================================
0. NON-NEGOTIABLE MIGRATION PRINCIPLES
==================================================

Before touching code, internalize these rules.

1. Django is the destination architecture.

2. Retirement of Django is NOT an acceptable resolution to migration problems.

3. Once migration begins, do not add new business logic to Next.js API routes unless explicitly required as a temporary rollback mechanism.

4. New backend features developed during migration belong in Django.

5. Every backend domain must have exactly one authoritative runtime owner.

6. Once a domain has successfully moved to Django production traffic, remove the corresponding authoritative Next.js implementation after the rollback window closes.

7. Do not maintain two permanent implementations of the same business behavior.

8. Django must ultimately own database schema evolution.

9. Do not simultaneously perform unrelated major infrastructure migrations such as:
   - Cloud SQL cutover
   - frontend framework replacement
   - storage-provider redesign
   - authentication redesign unrelated to Django cutover

10. Preserve current production behavior unless an explicit migration correction is required.

11. Migration progress must be objectively measurable.

12. If one Django domain fails in production, roll back THAT ROUTE temporarily and fix Django.
    Do not abandon Django.

13. Historical Django code must never override newer production behavior.

42. EXECUTION STYLE
==================================================

This is a large multi-stage migration.

Do NOT attempt a giant rewrite and then report success.

Work in verifiable gates.

However, do not stop after trivial reconnaissance.

Proceed through each safe stage until reaching the next operation that genuinely requires production authorization, irreversible deployment approval, credential input, or human review.

For implementation work that is local/repository-safe:

continue.

For production-impacting operations:

stop at the documented authorization boundary.

At every stage:

- inspect
- implement
- test
- compare
- document
- commit cleanly
- update migration status

Do not silently lower acceptance criteria to make progress appear complete.

==================================================
FINAL MIGRATION PHILOSOPHY
==================================================

The previous migration pattern was:

build Django mirror
→ leave production on Node
→ production evolves
→ Django drifts
→ parity becomes expensive
→ Django is retired

Do NOT repeat this.

The migration pattern now is:

declare Django authoritative destination
→ put Django in main
→ freeze new Node backend growth
→ build models from CURRENT production
→ transfer one domain
→ route real traffic
→ delete old owner
→ transfer next domain
→ Django becomes full API owner
→ Django becomes schema owner
→ migrate workers
→ remove Node backend

The migration succeeds when Django is no longer "the Django version of Veevee."

It succeeds when there is only one Veevee backend, and that backend is Django.
