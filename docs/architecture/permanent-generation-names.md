# Permanent generation names

Django assigns a canonical media name when a new generation first lands in a folder. Creation in a folder assigns it immediately; a new generation created in Unsorted keeps a provisional `unsorted_NNNN` name until first filing. The name uses the folder ancestry at assignment and a monotonic sequence from a library-wide counter keyed by that ancestry stem, compared case-insensitively. A renamed-away or recreated folder, a same-named folder in another project, and a folder name differing only in case therefore continue one numbering instead of reusing a name. The actual native media extension is resolved from the master, so unfinished work does not freeze an incorrect container extension.

`generations.permanent_name` stores the assigned stem. Later folder renames, folder moves, generation moves and project changes preserve it, its allocation namespace, sequence and assignment time. A database trigger rejects replacing or clearing it except through the explicit, audited admin action described below. Sequence allocation remains atomic, including the Green workers' private counter namespace (`VEEVEE_NAMING_PREFIX`, `apps/library/services/naming.py`). Deletion does not reset counters or make numbers reusable.

Seedance 2.5 draft finalization is the sole name-sharing exception. Every newly created final of a draft inherits exactly that draft's permanent stem through `assign_generation_naming`, including deliberate re-finalization after a prior final finishes. When an Unsorted draft is first finalized, it is frozen at the provisional `unsorted_NNNN` name it currently shows (its naming record's sequence) if no reservation holds that name library-wide, before either row can be filed elsewhere. The reservation index settles the claim, including a simultaneous finalize of another draft showing the same provisional name. Only when the name is already reserved do the draft and its finals receive a newly allocated library-wide `unsorted` name; the draft's naming record then stores the shown name in `fallback_from_name`, `provisional_name_reserved` in `fallback_reason`, and the fallback time in `assigned_at`. Freezing the draft's name advances its `updated_at`, so live updates deliver its final filename to connected clients. Generation IDs remain the identity for media, references, selection and exports. Each final retains an independent naming record and location; its displayed/download name comes from the shared permanent stem. Existing finals keep their previously assigned names.

`generation.0005_generation_name_owner` replaces the per-generation unique index from `generation.0004` with immutable reservations in `generation_name_owners`. A case-insensitive unique index on the reservation name and historical duplicate ordinal admits one owner per name, preserving the historical exceptions recorded by `0004`. A generation's nullable `name_owner_id` references its reservation; an ordinary generation owns its own ID, and only a matching Seedance draft final may reference the draft's owner ID. Database triggers enforce the exact name, owner and duplicate ordinal, prevent changing a shared lineage, and reject replacement or deletion of reservations. New ordinary names cannot use historical duplicate ordinals. Reservations survive generation deletion, so even a direct later assignment cannot reuse the name. Allocation checks reservations, including deleted generations' names.

Individual downloads and new ZIP media leaves use the canonical name, whichever library view or selection the ZIP was requested from: an export carries only generation IDs, and the manifest resolves each leaf from the generation's own name. New ZIP directories follow current organization. When a draft and its finals share a ZIP directory, they stay in it: the earliest selected final keeps the shared leaf (`Reel_Shot_0042.mov`), later finals take `_2`, `_3` in creation order (`Reel_Shot_0042_2.mov`) and the draft takes `_draft` (`Reel_Shot_0042_draft.mov`). If unrelated generations' canonical names collide in the same ZIP directory (historical duplicates), generation-ID subdirectories preserve each media leaf name; the same applies if a lineage leaf would itself collide or exceed path limits. Existing frozen export manifests and source media bytes remain unchanged.

Library cards display only the trailing sequence (`0042`); the full filename stays available on hover and as screen-reader text. Main chat displays the full name with the suffix always visible. Both labels overlay the top-left corner of the media without adding card height; library labels slide right when the selection checkbox appears. Chat fetches the open project/folder independently of the grid's search, media filter and global tabs, using the library's folder and Unsorted query semantics. New-generation receipts and live updates include the resolved filename immediately.

## Explicit rename to match folder

Admins can choose **Rename to match folder** from any folder kebab menu. Ordinary folder rename/move and generation moves still preserve names. The action previews the number of generations to rename, the number skipped, and an example old -> new name before confirmation. The preview is checked again when submitted; changed contents, ancestry or allocation require a fresh confirmation. A retry with the same idempotency key returns the original receipt, after checking admin authorization again.

The action includes all descendants and allocates fresh names using the existing atomic, case-insensitive library-wide stem counters. Already matching names are untouched. Within each target stem, allocation follows the previous trailing sequence, then creation time and ID for ties. Deleted and historical names remain reserved forever, including names relinquished by this action. Every renamed generation receives an immutable `generation_name_changes` receipt containing generation ID, old/new names, actor and time. A generation without a name yet is left to the ordinary first-naming path. This history survives generation/user deletion. Only the API role can execute the server-side database rename function; runtime roles cannot insert, update or delete audit receipts. The trigger allows only the exact old/new transition authorized by a receipt from that transaction. There is no general name-immutability bypass.

A shared draft/final lineage is renamed together only when every member is inside the selected subtree and every current path yields exactly the same stem. A lineage crossing the subtree boundary or spanning different stems is skipped in full; other generations still rename. Confirmation and results count the selected generations skipped whose names differ from their current path, and explain that their draft or final lives in another folder. No generation outside the subtree is renamed, and no shared name is split. Historical finals that have independent reservations retain their independent naming identity.

Queued and running generations participate immediately, without canceling or re-submitting paid work. Their names are library metadata, excluded from execution identity fences; worker completion changes execution/output fields while retaining the latest name. Subsequent finals inherit their draft's current reservation. Generation locks serialize rename and final naming, and reservation uniqueness prevents collisions with concurrent allocations. A concurrent allocation that invalidates the preview rolls back the action and asks for a new preview. Updated timestamps advance for every changed generation so live updates refresh other sessions; the initiating session refreshes the feed and chat immediately. New individual downloads and new ZIPs resolve the new names. Frozen export manifests and master media bytes remain unchanged.

`generation.0007_explicit_folder_name_rename` adds the audit table and replaces the two protection functions, without rewriting generations, counters, manifests or existing reservations. During an explicit rename, its database function changes the current reservation to the newly allocated name and inserts a separate immutable reservation for the old name in the same transaction, with no reusable gap. Reversal removes the new function/table and restores the previous protections while retaining all current names and historical reservations. Keep this additive migration during application rollbacks to preserve audit history. The deployment migration count becomes 68 (67 is `generation.0006_generation_cancellation_state`). This migration adds no data backfill; the controlled release still needs a brief writer maintenance window for trigger/function promotion, and the pending `0005` migration independently requires its documented write freeze. Upgrade tests cover shared names, nested folders, missing naming rows, historical duplicates, counters, immutable exports, explicit renaming, reversal and reapplication on real-shaped data. No production duration is inferred from fixtures.

## Upgrade

`generation.0003_generation_permanent_name` adds the nullable stem, freezes every existing generation at its current individual/download name (including existing Unsorted rows), and updates the deferred naming trigger. Historical rows without a naming record retain the old sequence-1 fallback name. The migration never rewrites existing export manifests or counters. It locks folder ancestry during the backfill; quiesce generation and folder writers for the controlled migration and keep them quiesced until compatible code is promoted, so old readers cannot expose mutable names during the rollout. `generation.0004_generation_unique_permanent_name` keeps every existing name, including names that already repeat (for example `unsorted_0001` in several projects). The earliest row of each repeated name keeps duplicate index 0 and later rows are numbered, so the unique index admits them while every new name must differ from all of them. It seeds each stem counter above the highest existing sequence for that stem; allocation also skips any number whose name is already taken. Both migrations run as part of a separately reviewed, controlled migration release; application startup does not migrate.

Before release, run `backend/manage.py audit_generation_names` against an approved database copy using the isolated test environment. The read-only JSON report provides the number of backfill rows, nested-folder rows whose new ZIP media leaf changes to match the existing individual download name, existing frozen export disagreements, and the groups of existing generations that share a name with their counts. Production counts require a separately authorized copy and are not inferred from synthetic fixtures.

The `0005` upgrade copies existing permanent names and duplicate ordinals into reservations without changing names, naming records, counters or export manifests. It adds only the reservation table and nullable owner reference, swaps uniqueness enforcement transactionally, and grants the existing API/worker roles SELECT/INSERT on reservations (the history role receives SELECT). **A short maintenance window is required:** drain generation/folder writers and workers before the controlled migration. The backfill and index swap hold the generation table lock; retain the write freeze until compatible code is promoted and verified. `library.0006_generation_naming_fallback` adds the two nullable provenance columns to `generation_naming` without rewriting rows; existing table grants cover them. Startup never migrates, and `deploy/legacy_config.py` accepts the resulting 66 migration rows. No production duration is inferred from synthetic fixtures.

The upgrade tests rehearse both previous migration states with nested folders, missing naming records, historical duplicate names, draft/final links, existing counters and frozen export manifests. Fresh-database tests apply the complete graph. Reversing `0005` restores the previous unique index and trigger, allocating additional historical duplicate ordinals to newly shared finals without replacing or clearing any permanent name. Reapplying `0005` preserves those names. Reversing `library.0006` drops only the provenance columns. Reversing `0003` removes permanent-name behavior; a release rollback should keep the additive migrations and roll back compatible code only.

## Authorization

Only admins may delete empty folders, delete any generation kind, or move generations through either single or bulk endpoints. These checks run before mutations and idempotent replay. Folder deletion is enforced in the shared `folder_engine.delete_folder` service, covering both `DELETE /api/folders` and the legacy `POST /api/projects` `deleteFolder` operation; missing or inactive actors cannot bypass the service guard. Active or uncertain paid generation evidence remains protected from deletion. Favorites and flags remain available to authenticated users. Folder creation, rename, recolor and folder move remain available to authenticated users, including moves of a folder containing generations.

Portraits, uploads, exports, material assets and canvas board permissions are unchanged. Django owns authorization; hidden frontend controls are an additional usability boundary.
